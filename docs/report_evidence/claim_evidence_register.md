# Phase 1A claim-evidence register

Audit date: 15 August 2026

This register reconciles claims needed for the final report's Introduction, Design, Implementation, Evaluation, and Conclusion. Repository code inspected during Phase 1A and the corresponding isolated execution outrank README, historical logs, and earlier report prose.

Source references use document names and the page numbers recorded during Phase 1A. References to `project template.pdf` use its printed handbook pagination; the cited pages are 10-12.

Status vocabulary:

- DEMONSTRATED: directly supported by the inspected code and fresh successful execution.
- STATICALLY SUPPORTED: supported by the inspected code but not freshly exercised on the stated path.
- PARTIALLY DEMONSTRATED: only a constrained part of the claim is supported.
- HISTORICAL ONLY: supported only by existing logs or an earlier document.
- PLANNED: intended future work/evaluation.
- UNSUPPORTED: no adequate evidence found.
- BLOCKED: an explicit environmental blocker prevented verification.

## Academic report constraints from instructions.txt

- Required chapters and maxima: Introduction 1,000 words; Literature review 2,500; Design 2,000; Implementation 2,000; Evaluation 2,500; Conclusion 1,000.
- The total ceiling is 9,500 words even though the individual maxima sum to more; front matter and references are excluded.
- Figures, tables, and diagrams do not count toward the word limit but must be relevant and discussed.
- The Evaluation chapter must cover methods, results, critical analysis, achieved objectives, limitations, and improvements across the project rather than treating a running prototype as sufficient evidence.
- Earlier feedback must be incorporated. The supplied feedback specifically requests more technical explanation/visuals, problematic-entry and edge-case analysis, broader positive/negative/edge testing, risk-oriented spike work, and usability evaluation.
- The `project template.pdf` minimum/good/outstanding descriptions are assessment context, not implementation evidence. Multi-composer browsing or authoritative external linking is an outstanding-level possibility, not proof of an implemented feature.

## Report-use boundary

The safest central claim for the draft final report is:

> Phase 1A inspection and execution demonstrated a reduced end-to-end transformation for four files classified as “Purpose-built, non-authoritative prototype fixtures informed by Carl Nielsen catalogue data and MEI structures.” The result comprised related PostgreSQL records, a read-only JSON API, and server-rendered catalogue pages. This establishes constrained technical feasibility, while general MEI reliability, authoritative Carl Nielsen fidelity, usability, performance, security, deployment readiness, multi-composer cataloguing, and field-level scholarly provenance remain unevaluated or planned.
